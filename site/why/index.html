cruthu / why

Why another container security tool

Because the baseline here is a signed build artifact, not a learned statistical model.

"A binary executed that isn't in the SBOM" is a fact, not an anomaly score. That difference decides almost everything else about the tool: no training period, no false-positive tuning treadmill, and an explanation you can hand to an auditor without a footnote about model confidence.

Existing in-use analysis lives locked inside vendor platforms. cruthu is the vendor-neutral, SBOM-standard-native version, and its output is a portable signed artifact rather than a seat in someone's console. The evidence is the product, not the dashboard.

The failure mode that actually matters

Most security review asks one question: can this be exploited? A drift detector has a second failure mode, and for this product it is the worse one — drift that goes unreported. A tool that misses the cryptominer is worse than no tool at all, because it converts an unknown into a false assurance. Someone reads the green check and stops looking.

So the project's house rules put a standing question in front of every change to the reconciler, the index, the path-matching logic, or the event adapters:

Construct an event that represents real drift but that this code would classify as clean.

If you cannot construct one, say why not. If you can, that is a bug in the change, not a corner case. A false negative that hides drift is treated as more serious than a crash.

What that buys you, concretely

  • Error paths fail closed. A parse failure, an unreadable index, or a truncated event stream exits 2, never 0. A pipeline can never read "the tool broke" as "the image is clean."
  • Path normalization is treated as detection logic, not string formatting. Any change to how paths are compared can silently create an evasion, so it gets the question above. Directory-symlink aliasing — /usr/bin against /bin, and the rest of the usrmerge layout — is resolved in the index rather than papered over at compare time.
  • Every suppression is a hole in the detector. No allowlist or "known noise" default is widened without a test proving the specific noise is suppressed and a comment justifying it.
  • Untrusted input is bounded. SBOMs from registries, event streams off sockets, and filesystems from arbitrary images are hostile by default: no allocation sized from a file, no panic on malformed input, and confinement checks on every path derived from input. Image filesystems are opened with os.OpenRoot, not os.DirFS, because the latter follows a symlink out of its own tree exactly as os.Open would — a distinction recorded in the decision log.
  • Every parser of untrusted input has a fuzz target, run short in CI and long nightly.

What it will not catch

Worth stating plainly, because a breadth claim you can disprove in an afternoon costs more trust than a narrow claim you can verify:

  • Interpreted application code. Python and Node source is not "packages." v1 scopes its claims to binaries and shared objects. Application-code integrity is dm-verity and IMA territory, and it is not a v1 promise.
  • Whatever your workload never exercised. In-use and debloat output is only as good as the code paths that actually ran. The debloat report says so, prominently, every time.
  • File-level gaps in the SBOM itself. Most SBOMs lack file lists, which is why cruthu owns the index step rather than trusting the SBOM to be the authority on paths.

How the code gets to that bar

cruthu is developed with AI assistance under a documented, review-first process: every change is specified before it is written, reviewed by a human before merge, passed through automated security tooling and continuous fuzzing of all untrusted-input parsers, and given an independent adversarial review pass by a session that did not write it. The governing rule is that no line merges which a human maintainer cannot explain and defend — what it does, why it is correct, and why it is safe against hostile input.

We hold a security tool to a higher bar and document how we meet it, rather than hoping nobody asks. The rules themselves are in the repository, in CLAUDE.md and CONTRIBUTING.md.

Found a false negative?

If you can construct an event stream representing real drift — an executed binary or a loaded library absent from the SBOM — that cruthu reports as clean, that is a security-relevant finding and we want it through the private channel in SECURITY.md, not a public issue.
